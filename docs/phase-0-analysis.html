01The problem, restated

Oncology data arriving as FHIR R4 is structurally valid far more often than it is fit for purpose: references dangle, profile-mandatory elements are absent, staging is scattered across four sibling Observation resources that must be reassembled into one concept, and dates arrive at inconsistent precision. OncoBridge ingests synthetic FHIR R4 bundles, stores every source resource verbatim and immutably, normalizes a deliberately small set of oncology concepts into a canonical domain model that is not FHIR-shaped, evaluates each import against a named and individually-cited set of deterministic data-quality checks spanning structural, conformance, referential and domain-consistency classes, and records the lineage linking every normalized entity back to the source resources and transformations that produced it — then exposes all four layers through a REST API and an Angular inspector that renders source → normalized → quality → provenance for any single concept. The engineering problem is not "read FHIR"; it is maintaining a rigorous, inspectable, reversible boundary between an external interchange format and an internal domain model, and making every judgement the system reaches auditable back to a published specification statement.

02Who this is actually for

Being honest about this changes the design, so it is worth stating plainly. There are two real users and one fictional one.

Primary — the technical evaluator

A hiring engineer, tech lead, or architect who will spend ten to twenty minutes in the repository. They will read the README, skim the ADRs, open one or two source files, and possibly run it. Every design decision below is optimized for this person: the ADR list, the architecture test that enforces the FHIR/domain boundary, and the four-pane inspector exist because they make the architecture legible in minutes. A beautiful timeline chart does not.

Secondary — the interoperability-literate reviewer

Someone who knows FHIR and will check whether the standards claims are accurate. This user is the reason every conformance check carries a citation field and the reason the UI must never say "mCODE validated" when it means "passed six OncoBridge checks."

Fictional — the data steward

The in-universe persona: someone triaging an inbound oncology data feed who needs to know what arrived, what is wrong with it, and where each normalized value came from. This persona exists to keep the feature set coherent. It is not a real user and must not be used to justify scope. Every time a feature is proposed "because a data steward would want it," that is the moment to check whether it also serves the primary user.

03What OncoBridge is not

These distinctions are load-bearing — they are what keeps the project both scoped and legally safe.

Not a…BecauseObservable difference
Cancer registryA registry's purpose is complete, longitudinal, standards-abstracted case capture for population reporting, with human abstractors and mandated data dictionaries. OncoBridge captures whatever arrives and reports on its shortfalls.A registry fills gaps; OncoBridge reports them and stops. No manual entry, no abstraction workflow, no case completeness target.
EHRNo encounter workflow, no orders, no scheduling, no clinical authoring, no user-to-patient care relationship. Data is write-once at import.There is no "edit patient" screen anywhere in V1, by design.
Generic FHIR viewerThis is the distinction most at risk of collapsing. A viewer renders resources. OncoBridge transforms them into a model with different shape, different cardinality and its own invariants — most visibly by collapsing four staging Observation resources into one composite value object.If the normalized model ever looks like a prettier Bundle, the project has failed. The staging composite is the proof that it doesn't.
Decision supportEvery rule is structural, referential, or temporal-ordering. None interprets a clinical value, suggests an action, or scores a patient.No check reads a tumour marker value. No output contains an imperative verb directed at care.
Naming discipline follows from this

The "generic FHIR viewer" risk is mitigated by architecture. The "decision support" risk is mitigated by vocabulary, and it must be enforced in code, not just in a disclaimer: the API returns findings, never errors or alerts; a check is OB-CONF-002, never StagingIncompleteWarning; no route, type or field name in the codebase may contain diagnose, assess, recommend, risk, or clinical. This is cheap to hold from day one and expensive to retrofit.

04Challenging the proposed V1

The hypothesis proposed five concepts. Two of them do not earn their place, and one of them is carrying the entire architecture without having been identified as doing so.

ConceptVerdictReasoning
Cancer stage Keep — core This is the architectural centre of the project and should be protected at all cost. The mCODE TNMStageGroup profile uses hasMember to reference the T, N and M category observations — verified: hasMember:TNMCategory is 0..3 and Must Support. That means a graph in the source must become a single composite value object in the domain. That one fact exercises referential integrity checking, cross-resource aggregation, conflict detection, and a genuine domain invariant. It is the single strongest argument that OncoBridge is not a FHIR viewer.
Primary cancer diagnosis Keep — anchor The anchor entity everything else hangs from, and the source of the most realistic conformance failures on synthetic data. Non-negotiable.
Patient Keep — minimal Necessary plumbing and the subject of the cross-patient integrity check. Deliberately shallow: identifier, birth date, sex-at-birth-as-recorded. Nothing else. It is not a showcase and should not be treated as one.
Treatment / procedure Keep — narrowed Narrowed to surgical procedure only. It earns inclusion for a different reason than the others: it is the only concept introducing a second date polymorphism (Procedure.performed[x] as dateTime or Period, distinct from Condition.onset[x]), and a timeline needs more than one event type to be a timeline. This is the one concept included partly for demonstrative rather than architectural reasons — and therefore the first thing to cut if Phase 3 overruns.
Tumour marker / biomarker Cut from V1 The weakest proposal, and cutting it is the most important recommendation in this section.
Why tumour markers are cut

Architecturally, TumorMarkerTest is just another Observation — structurally identical to the staging observations already being handled. It adds no new boundary, no new relationship shape, and no new persistence concern. What it does add is the hardest problem in the entire domain: UCUM unit normalization, comparator semantics (<, > on Quantity), reference-range interpretation, and value-set membership across a large LOINC space. Doing that properly requires a terminology service. Doing it improperly means inventing medical judgement — precisely what the brief forbids.

It is the textbook case of a feature that sounds impressive and delivers weak software-engineering value per unit of risk. Cut it, and say in the README that it was cut deliberately and why. A reviewer who sees a documented, reasoned exclusion reads competence; a reviewer who sees a half-implemented biomarker module reads the opposite.

Verified against HL7 — and it changes the design

mCODE STU4 (v4.0.0, published 16 Feb 2025) is the current published version, built on FHIR R4, with roughly 40 profiles in six thematic groups.

More consequentially: Synthea cannot emit mCODE-conformant output directly. MITRE's mCODE test datasets were produced by post-processing Synthea output through a separate fhir-mapper step. This is not an inconvenience — it is the project's justification. It means raw Synthea oncology bundles genuinely fail mCODE expectations, so the conformance engine reports real findings on real synthetic data rather than contrived ones. It is also the reason ingestion must never require mCODE (§7).

Data source recommendation

Use Synthea (Apache-2.0) breast-cancer-module output as the primary corpus — its breast cancer module is among its most developed — supplemented by small hand-authored bundles that trigger exactly one check each. Optionally cross-check against MITRE's published mCODE test data, which is distributed free of cost, privacy and security restrictions. Every fixture lands under test-data/synthetic/ with a README naming its generator, version and licence.

07Where mCODE earns its place — and where it doesn't

The brief asked directly whether mCODE is necessary. The answer is yes, but in exactly one role, and getting the role wrong is the main way this project turns into architecture astronautics.

RoleVerdictWhy
mCODE as the conformance yardstickGenuine valueIt supplies published, citable, mandatory-cardinality statements that synthetic data measurably fails. Without it, "data quality" would have to be invented — which is the forbidden path. This single role justifies the dependency.
mCODE as an export targetGenuine value — laterProjecting the canonical domain back out as mCODE-shaped FHIR proves the boundary is bidirectional and that normalization was not lossy in the ways that matter. Strong closing phase.
mCODE as the ingestion contractRejectWould reject nearly all realistic synthetic input, including Synthea's, and would collapse the interesting failure modes the project exists to surface.
mCODE as the internal domain modelRejectExplicitly forbidden by the brief and correctly so. It would make the domain a FHIR profile with extra steps and destroy the project's thesis.
Full profile validation via the Firely validatorPostponeSee below — the reasoning here is subtle and worth an ADR.
Recommendation — hand-written cited checks, not a general validator

Running the real StructureDefinitions through a full FHIR validator sounds more rigorous, and in a production system it would be. For V1 it is the wrong call, for three reasons. Explainability: a validator emits a flat list of machine messages — the four-pane inspector needs a finding it can narrate, with an expected value, an actual value and a citation. Noise: required bindings to SNOMED and LOINC value sets cannot resolve without a terminology server, producing failures that say more about the test rig than the data. Churn: the validation packages version independently of the core SDK, which is a maintenance surface a portfolio project should not carry.

V1 therefore implements six named checks, each derived from a specific cited specification statement. This must be labelled honestly everywhere it surfaces: "OncoBridge conformance checks — a subset of mCODE STU4", never "mCODE validated." Full-validator integration is a legitimate later phase and a good ADR supersession story.

The non-obvious decision — where findings attach

Conformance and structural findings attach to the source resource. Domain-consistency findings attach to the domain entity. This is not a filing convenience; it follows from what each finding is a statement about. "This Observation lacks its mandatory method" is a claim about the input and stays true forever, even if normalization is later rewritten. "This staging assessment predates its diagnosis" is a claim about our normalized result and could legitimately change when the mapper changes.

The practical payoff: re-running normalization with new mapper logic must invalidate domain-consistency findings and must not touch conformance findings. That falls out cleanly from this split and is a mess without it. Worth ADR-0004.

10Provenance model

Three tiers, each answering a different question.

TierAnswersKey fields
ImportBatchWhen did this arrive, from where, and what happened to it?Id, SourceSystemLabel, ReceivedAt, FileName, RawPayload (bytea, exact bytes), ContentHash (SHA-256 over exactly those bytes), BundleType, EntryCount, Status, NormalizerVersion
SourceResourceExactly what did we receive, byte for byte?Id, BatchId, ResourceType, SourceLogicalId, FullUrl, ContentHash, EntryIndex, and (P2) a parsed jsonb copy for querying — not the audit representation
LineageWhich sources, through which transformation, produced this value?DomainEntityType, DomainEntityId, FieldPath (nullable), SourceResourceId, TransformationName, TransformationVersion
The real design tension — lineage granularity

Field-level lineage for every property is more impressive in a diagram and considerably worse in practice: it multiplies row count by an order of magnitude, couples every mapper to a lineage-recording API, and produces a UI panel nobody reads.

Recommendation: entity-level lineage as the default, with field-level records emitted only where a domain entity draws from more than one source resource. In V1 that condition is met by exactly one concept — CancerStaging, which pulls its group from one Observation and each category from another. So field-level lineage appears precisely where it carries information, and nowhere else. FieldPath is nullable for exactly this reason: null means "this entity, wholly, from this source."

The payoff is visible in the inspector: the staging composite shows four lineage rows naming four distinct source observations. That single screen demonstrates graph-to-aggregate normalization and multi-source provenance simultaneously — and it is the screenshot that belongs in the README.

Do not use FHIR Provenance internally

FHIR R4 Provenance is a reasonable export projection — target is 1..*, recorded is 1..1, entity.role includes derivation, and the specification explicitly contemplates "an automaton that transforms input," which is precisely what a normalizer is. But adopting it as the internal model would repeat the mistake the brief warns against in §7. Model provenance in OncoBridge's own terms; project to Provenance at the export boundary in a later phase.

11Data-quality semantics

Four finding categories, ordered by the pipeline stage at which each becomes detectable. The ordering matters: a category can only be evaluated if every category above it passed.

CategoryDetected atQuestionSeveritiesBlocks normalization?
StructuralParseIs this valid FHIR R4 at all?ErrorYes — resource never enters the domain
ConformancePost-parseDoes it meet the mCODE STU4 expectation?Error WarningNo
ReferentialIntegrityBundle resolutionDo its references resolve, and to the right thing?Error WarningPartially — may leave an aggregate incomplete
DomainConsistencyPost-normalizationIs the normalized result internally coherent?WarningNo

Severity is derived, not chosen

Assigning severity by intuition is how a quality tool becomes untrustworthy. The rule is mechanical:

  • Error — the specification says mandatory (min cardinality ≥ 1), or the check is a pure structural/graph fact with no interpretation.
  • Warning — the specification says Must Support, or the binding is extensible rather than required, or the finding is a domain-consistency observation.
  • Information — coverage and context notes only.
The fifth outcome — and it is not a finding

A resource type outside V1 scope, or an onset[x] arriving as Age when V1 handles dateTime and Period, produces a CoverageNote — a distinct type, not a Finding. Conflating "we did not look at this" with "this is wrong" is the most common failure mode of real data-quality tooling, and it destroys user trust in every other number on the screen. Keeping them as separate types makes the conflation impossible rather than merely discouraged.

Finding shape

Every finding carries: CheckId, Category, Severity, Message (deterministic template — same input, same string, always), Target (source resource or domain entity per §8), Expected / Actual where meaningful, and Citation — the published specification statement it derives from. Citation is not decoration. It is what makes each check auditable, what proves the rules were derived from public standards rather than from anywhere else (§20), and what lets a reviewer verify a claim in thirty seconds.

12The six V1 checks

All six are deterministic, individually citable, and free of medical judgement. Every category from §11 has at least one.

IDCheckSeverityBasis
OB-STR-001 Bundle entry does not parse as FHIR R4. An entry's JSON fails deserialization into a known R4 resource. Error Structural. Zero interpretation. The resource is recorded verbatim but does not enter the domain.
OB-REF-001 Reference does not resolve within the bundle. A Reference.reference on an in-scope resource matches no entry fullUrl, contained resource, or resolvable identifier in the same bundle. Error Pure graph fact. Scoped to within the bundle — V1 makes no external resolution attempt, and says so in the message.
OB-REF-002 Staging group members disagree on subject. A TNMStageGroup's hasMember targets resolve to observations whose subject differs from the group's own. Error Verified: subject is 1..1, hasMember:TNMCategory is 0..3. A graph-consistency check with real teeth — it is the check that would catch a genuine record-linkage defect.
OB-CONF-001 Primary cancer condition lacks a required category. No Condition.category coding satisfies the US Core problem/health-concern slice. Error Verified: category:us-core is 1..* with a required binding in mCODE STU4. Error is therefore justified by cardinality, not opinion. Fires on real Synthea data, which commonly emits encounter-diagnosis.
OB-CONF-002 TNM stage group omits staging method. Observation.method is absent. Error Verified: method is 1..1 mandatory on the STU4 TNMStageGroup profile. The cleanest check in the set — unambiguously mandatory, and routinely absent in synthetic data.
OB-DOM-001 Staging assessment precedes diagnosis onset. Where both dates are known and comparable, staging effective is Before diagnosis onset. Warning Temporal ordering only — no clinical claim. Warning because legitimate backdating exists. Fires only on TemporalComparison.Before, never on Indeterminate (§13).
Stretch check, if Phase 4 has room

OB-CONF-003 — cancer condition code is not drawn from an expected code system (Warning). Condition.code has an extensible binding in STU4, so a non-matching code is explicitly not an error — and getting that severity right is itself a demonstration of standards literacy worth more than the check. Implemented as a code-system-URI membership test (SNOMED CT or ICD-10-CM), never a value-set expansion, so it needs no terminology server. The message must state that limitation plainly rather than implying value-set validation.

Explicitly not checked in V1

No check reads a clinical value and judges it. Nothing evaluates whether a stage is plausible for a diagnosis, whether a procedure suits a stage, or whether any value falls in a reference range. Those require medical judgement, and their absence is a design decision to be stated in the README — not an omission to be quietly filled later.

13Date and time semantics

This is the most underestimated problem in the project and, handled properly, the strongest pure domain-modelling showcase in it.

The problem

FHIR date and dateTime are variable precision: 2019, 2019-03, 2019-03-14 and 2019-03-14T10:00:00+02:00 are all valid. Mapping any of these to DateTime silently fabricates precision — 2019 becomes 2019-01-01T00:00:00, and every downstream comparison is then confidently wrong. Almost every naive FHIR integration has this bug.

The model

  • PartialDate — (Value, Precision ∈ {Year, Month, Day, Instant}). Precision is never inferred and never widened.
  • Three-valued comparison — Compare(a, b) → Before | After | Same | Indeterminate. 2019 vs 2019-03 is Indeterminate: March 2019 is inside 2019, so no ordering exists. Returning Before or After there would be a lie the type system can prevent.
  • Rules consume the four-outcome result honestly. OB-DOM-001 fires only on Before. Indeterminate never produces a finding — it may produce a CoverageNote. This single rule is the clearest evidence in the codebase that the problem was understood rather than papered over.
  • Timezones — preserve offsets when present; never assume server-local. Persist instants as timestamptz, partials as value plus precision tag.

Three distinct clocks — never conflated

ClockMeaningSourcesUsed for
Clinical timeWhen the thing happenedCondition.onset[x], Observation.effective[x], Procedure.performed[x]Timeline ordering; OB-DOM-001
Authoring timeWhen the source system recorded itCondition.recordedDate, mCODE assertedDate extensionContext only; never ordering

V1 polymorphism scope: onset[x] and performed[x] support dateTime and Period only. Age, Range and string produce a CoverageNote — never a finding, because the data is not wrong; V1 simply does not read it.

14Terminology boundary

Drawn deliberately tight. Terminology is where portfolio projects go to die: it is unbounded, and no amount of effort produces a visibly better result.

V1 doesV1 does not
Store codes as CodedConcept(System, Code, Display), carried through unchanged — no code is ever rewritten Run or embed a terminology server
Recognize code systems by URI only — http://snomed.info/sct, http://loinc.org, http://hl7.org/fhir/sid/icd-10-cm, http://unitsofmeasure.org Expand value sets or test membership
Use one small, checked-in, cited lookup table for a single purpose: identifying staging observations by LOINC code (21908-9, 21902-2, 21914-7 for the stage group, plus the T/N/M category codes) Perform subsumption, hierarchy or concept mapping
Version and cite that table as data, in-repo, reviewable in a diff Translate between code systems
Licensing constraint that shapes the code

SNOMED International charges nothing for Affiliate Licensing within Member countries, but a licence is still required, licences are per-country, and non-Member use may attract a fee. LOINC carries its own terms. The practical rule that follows: the repository may contain code references, never terminology content. Storing the code 254837009 that appeared in a synthetic bundle is fine. Checking in SNOMED description files, hierarchy extracts or a display-name lookup table is redistribution and must not happen.

This is a real constraint with a real design consequence: CodedConcept.Display is populated only from what the source bundle supplied. OncoBridge never enriches a display name from its own table. That is a licensing-driven decision, and it is worth one line in the ADR so a reviewer sees it was deliberate.

Recommendation — PostgreSQL

Corrected after review: the original draft claimed jsonb could serve as the byte-for-byte audit record. It cannot — jsonb is a parsed form and may reorder keys, drop whitespace and renormalise numbers, so a digest over it will not match one over the received bytes. The audit record is ImportBatch.RawPayload stored as bytea; jsonb earns its place only for semantic querying of parsed resources. See ADR-0006. The jsonb argument is therefore weaker than first stated but still real, and PostgreSQL still wins on the practical grounds below. The Apple Silicon / one-command-run argument is the tiebreaker: a portfolio project a reviewer cannot start in thirty seconds has failed at its actual job.

Stated honestly: if the target audience is a Microsoft-stack shop, this is a real trade. The mitigation is architectural rather than aspirational — keep every raw-JSON query behind a repository interface in Infrastructure, so no jsonb operator ever appears in Application or Domain. With that discipline the provider swap is roughly a day's work. Without it, it is a rewrite. This is precisely why the "must never leak jsonb past a repository interface" rule appears in §15.

Verified on this machine: Docker 28.5.1 present, no local PostgreSQL — so compose it, and pin the image tag.

18First acceptance scenario

One synthetic bundle in, four inspectable layers out. The fixture is engineered to fail in exactly three named ways — a scenario that only proves the happy path proves very little, and the failure paths are the product.

High Disclaimer in README first paragraph, DISCLAIMER.md, and a persistent UI banner — but the effective control is the naming discipline in §3, enforced in code. ▸Final output

1 · Recommended V1

A locally-run modular monolith that ingests a synthetic FHIR R4 bundle, stores every source resource verbatim and immutably, normalizes four oncology concepts into a canonical non-FHIR domain model, evaluates six named and individually-cited deterministic quality checks across four categories, records multi-source lineage for every normalized entity, and exposes all four layers through a REST API and an Angular inspector rendering source → normalized → quality → provenance.

2 · Recommended domain concepts

Patient · PrimaryCancerDiagnosis · CancerStaging (composite: stage group + up to three StageCategory) · CancerSurgicalProcedure. Supported by PartialDate, CodedConcept, Finding, CoverageNote, ImportBatch, SourceResource, Lineage.

3 · Recommended source FHIR resources

Bundle · Patient · Condition · Observation (TNM stage group + T/N/M categories) · Procedure. Measured against mCODE STU4 profiles; conformance to them is never required for ingestion.

4 · Recommended solution boundaries

Domain (zero dependencies) · Application · Interop.Fhir (sole owner of Hl7.Fhir.*) · Infrastructure · Api · oncobridge-web, plus three test projects. Modular monolith. The FHIR/domain boundary is enforced by an automated architecture test.

5 · First acceptance scenario

One synthetic bundle containing three deliberate defects → 201 with a batch id → 7 verbatim hashed source resources → 4 normalized entities including a staging composite assembled from 4 observations → exactly three findings (OB-CONF-001, OB-CONF-002, OB-REF-001) → 4 lineage records → rendered in the four-pane inspector. Full detail in §18. This is the phase gate.

6 · First ADR list

ADR-0001 domain independent of FHIR · 0002 mCODE as boundary not contract · 0003 immutable source, derived normalization · 0004 four finding categories and attachment rules · 0005 variable-precision temporal model (PartialDate, PartialPeriod, TemporalComparison) · 0006 PostgreSQL with bytea raw payloads · 0007 modular monolith with enforced boundary · 0008 cited checks over general validator · 0009 no terminology server in V1.

7 · Proposed phases

P1 domain foundation · P2 ingestion & provenance · P3 normalization · P4 quality engine · P5 API · P6 Angular inspector then timeline · P7A release polish (mandatory) · P7B mCODE export (stretch). Each with a hard gate (§23).

8 · Explicit non-goals

Not a registry, not an EHR, not a FHIR viewer, not decision support. No DICOM/DICOMweb, no SMART on FHIR, no authentication, no real EHR integration, no tumour markers, no medications, no genomics, no terminology services, no full profile validation, no large populations, no cross-batch patient matching, no advanced deployment, no microservices/Kafka/Redis/event sourcing/CQRS/AI.

▸Verdict

Phase 0 assessment

Green light — with changes

The project is feasible, the scope is defensible, and the architecture has a genuine thesis rather than a feature list. It is approved to proceed to Phase 1 subject to the following changes, all of which narrow scope or sharpen a boundary.

Required changes to the proposed V1

  1. Cut tumour markers / biomarkers. Architecturally redundant against the staging observations, and the only concept in the proposal that would require inventing medical judgement. The single most important change here.
  2. Narrow treatment to surgical procedure. Medications are a separate normalization problem and belong to a second slice.
  3. Promote staging to the architectural centre. It was listed as one concept among five; it is in fact the concept carrying the project's entire claim to not being a FHIR viewer. Build it first in Phase 3.
  4. Add PartialDate and PartialPeriod as first-class domain concepts, compared through a four-outcome TemporalComparison. Not implied by the original proposal, and their absence would have produced a silently wrong system.
  5. Fix mCODE's role: conformance yardstick and export target only, never an ingestion requirement. Justified by the verified fact that Synthea cannot emit mCODE directly.
  6. Adopt six cited checks rather than a general profile validator for V1, recorded as an explicitly reversible decision.
  7. PostgreSQL, with all raw-JSON access held behind a repository interface.
  8. Adopt the naming discipline in §3 from the first commit. It is the effective control against medical-device language, and it is expensive to retrofit.

Standing hazard

The most likely way this project fails is not technical — it is an incomplete vertical slice caused by adding concepts before §18 passes end to end. Treat the acceptance scenario as a hard gate. Four concepts finished beats six concepts half-built, every time.
